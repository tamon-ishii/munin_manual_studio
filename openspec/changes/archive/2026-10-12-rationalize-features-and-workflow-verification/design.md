# Design

## Context

目的は proposal.md を参照。画面は index.html と main.ts、動的な画像カードは resourceBrowser.ts / screenshotLibrary.ts、撮影・作画・Diffは別モジュールで組み立てる。既存仕様には原本保持、候補採用、通常画像の編集コピー、旧形式読み取りの異なる契約がある。

現在の build.yml はLinuxで unit/ui/generation/capture/smoke を実行する。check_manual_studio.mjs の native はRust検査で、実OS操作とは異なる。smoke_manual_markits_native.mjs はMarkItsを直接起動し、Studioのカードからの起動を確認しない。旧AIタグ前提のテストや説明は現行仕様との整合確認が必要。

## Goals / Non-Goals

**Goals:** 利用目的を単位に全機能の存在理由、入口と終点、異なる保存契約、確認証拠を追跡する。登録漏れと未実行を検査失敗にする。削減より作業の連続性を優先する。

**Non-Goals:** 本変更でユーザー向け機能を削除・改名しない。AIモデルの応答品質や全OSをモックで保証しない。移行データを消さない。

## Decisions

### 1. 機能の見直しと検査を同じ台帳に結び付ける

レビュー台帳を docs/manual-studio-feature-review.md に置く。機能ID、利用目的、全入口、実装モジュール、結果と保存範囲、元へ戻る方法、対応仕様、シナリオID、必要証拠、判断・根拠を記録する。表示箇所の数を機能数として数えない。同一操作を複数箇所に置くことは、文脈に合うなら維持する。

判断は「維持」「入口統合」「処理統合」「詳細へ移動」「廃止検討」。利用頻度は計測がないため推測で断言しない。独立した用途があるか、結果を予測できるか、作業場所で開始できるか、反復入力・往復・選択喪失・確認の重複があるかを実操作で測る。単純なメニュー削減案は保存契約の差を隠すため採用しない。

### 2. 文脈付きの共通処理を検討する

将来の統合では開始時に project/document/revision/cursor/resource/revision/returnTarget を保持し、明示的に完了または中止する。画像挿入、比較、候補確認、進捗と再試行の共通処理から入口ごとの差分だけを渡す。通常画像のコピー、管理画像の候補採用、参照差し替えは別の結果種別として保持する。異なる結果を同じ「保存」で隠さない。各UI変更はレビュー結果から別の仕様変更にする。

### 3. 実行可能な検査台帳

scripts 配下へ機械可読の機能/action/シナリオ/ケース台帳とvalidatorを追加する。実画面探索はDOMのbutton/summary/menuitem/link/inputに加え、ショートカット登録とdrag/dropハンドラーの静的照合を行う。動的状態の探索には未選択、通常原稿、選択あり、画像種類、保護、候補あり、処理中、失敗を用意する。未知の操作、シナリオのない入口、収集できない操作は未確認としてゲートを失敗させる。action IDはまずテストアダプターで収集し、必要な安定IDだけ段階的に追加する。

ケースごとに前提、操作、目に見える結果、保存結果、保持状態、復帰先、証拠種別を必須にする。クリック数やinvoke回数だけを成功条件にしない。browser-mock / real-backend / real-desktop / real-provider は別の証拠欄とし、必要な欄の欠落を失敗扱いにする。シナリオ・ケース・ソースとビルドのハッシュ・OS・時刻・状態ログ・画像を結果へ保存する。

### 4. 結果と効率を別々に評価する

機能の正しさはファイル・版・原稿・Undo・復帰状態で確認。使いやすさは入口を探す回数、パネル往復、同じ情報の再入力、意味の同じ確認、戻ったときの保持、進行を妨げるフォーカスで評価する。経過時間はAI応答待ちとUI操作時間を分ける。画面を新たに覚え直すより、作業場所へ入口を置く案を優先する。

### 5. CIと検査の有効性

既存のLinuxブラウザー検査は維持し、台帳照合と証拠validatorを追加する。隔離したLinux実デスクトップでStudio→MarkIts→復帰→比較→採用を実行し、保存形式の配列/elements、使用原稿あり、子プロセス異常終了を必須にする。Windows/macOSは対象のOS連携を変更するリリースで必要証拠を要求し、未実行を合格表示しない。Linux通過を他OS通過と解釈しない。

変換形式を壊す、復帰時に親入力を消す、未知のボタンを追加する、証拠を欠落させる故障を別々に入れ、対応ゲートが失敗することを確認する。故障注入は一時コピー/隔離環境で行い、ユーザーの作業ツリーを変更しない。

## Risks / Trade-offs

- 動的画面と独自ジェスチャーの収集漏れ → DOM探索と登録コード照合を併用し、未対応を明示。全探索の保証はしない。
- ネイティブ検査の環境依存 → 専用デスクトップ・自作fixtureアプリ・プロセス所有確認・段階別タイムアウト。AI出力は決定的なテスト応答を基本とし実提供元の確認を区別。
- 共通化で資産ごとの差が失われる → 台帳に原本/候補/採用/コピー/参照変更の契約を明記し、変更時に仕様差分を作る。
- 全ケースの組合せ爆発 → 各遷移と連続2遷移、データ損失・外部連携の故障を優先する。未確認範囲を報告する。

## Migration Plan

台帳と現状の証拠を整備→MarkItsの実経路→照合ゲート→全作業へ展開→個別の統合変更。旧形式データをfixtureに含め、既存機能とテストを維持したまま追加する。ゲート問題は専用変更を戻せるよう分離し、未確認の除外を合格扱いにしない。
