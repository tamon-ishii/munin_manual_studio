# UI操作の検査漏れを検出する仕組み（設計案）

状態: 提案。以下の仕組みは未実装であり、現在の検査を網羅済みとする根拠にはしない。

## 問題

テスト成功は、登録された入力と経路の成功だけを示す。操作がテストから抜けていても成功する。MarkItsのネイティブ検査は直接起動するため、Studioのボタン→保存済み画像の読み込み→メタデータ変換→MarkIts起動という経路を確認できなかった。画面要素の配列形式は動作したが、AI撮影で保存される `{elements:[...]}` 形式で起動前に失敗した。

現在の `.github/workflows/build.yml` はLinuxで `scripts/check_manual_studio.mjs` のunit/ui/generation/capture/smokeを実行する。前回調査からブラウザー検査の接続状況が更新されている。Windows/macOSの実ウィンドウ検査は手動実行オプション。`native` という検査グループにRust単体テストが含まれ、実ウィンドウの操作済みとは区別しにくい。

## 1. 全操作の登録と画面からの照合

各操作を安定したaction IDで登録し、表示条件、開始状態、成功状態、失敗状態、戻り先、保持すべき入力、対応する作業シナリオを定義する。新しい操作はシナリオへの対応がないと検査を失敗させる。

操作一覧を人が書くだけでは同じ漏れを再発する。実際に開いた画面からbutton、menuitem、リンク、入力変更、ドラッグ操作、キーボード操作を収集し、登録表と双方向で照合する。動的なメニュー、画像カード、空状態、保護済み、編集中、エラー状態を探索対象に含める。発見した未登録操作と、表示するはずなのに到達できない操作を別々に報告する。

共通の操作登録・状態管理からUIと検査一覧を生成する。登録されたボタンだけを巡回して網羅と称する仕組みにはしない。action IDの記録だけでは合格にせず、結果状態のアサーションを必須とする。

## 2. ボタン単位ではなく、一連の作業を検査する

| 作業ID | 最初から最後までの経路 | 成功時に確認する結果 |
| --- | --- | --- |
| resource-edit | リソース一覧→MarkItsで編集→実ウィンドウ→注釈追加→編集終了→Studio復帰→比較→採用 | 原本と採用済み画像を候補保存まで保持し、採用後に使用原稿の画像が更新される |
| review-correct | 文書→レビュー→該当箇所→修正指示→Diff→部分採用→次の指摘 | 引用箇所、結果の保持、採用・見送りの反映、原稿変更時の安全な扱い |
| selection-create | 選択範囲またはカーソル→指示→生成→Diff→採用→Undo | 範囲外を保持し、挿入位置・Undoが正しい |
| image-insert | 作画→履歴選択→画像比較→挿入先→挿入 | キャンセルしても指示・選択画像を保持し、採用時だけ正しい原稿へ挿入 |
| ai-capture | エディタ→指示→アプリ調査・登録→起動→ウィンドウ選択→手順確認→撮影→注釈→確認→挿入 | 実ウィンドウ・再撮影手順を保存し、失敗した工程だけ再試行できる |
| manual-capture | エディタ→手動撮影→記録→撮影→MarkIts→確認→挿入 | AI不要、元のカーソルへ挿入し、キャンセル時に本文を保持 |
| recapture-adopt | 使用中の画像→再撮影→差分比較→採用 | 失敗時は既存画像を保持し、採用した版だけを使用原稿へ反映 |
| document-switch | 複数原稿の編集→移動→保存失敗・未保存確認→復帰 | 未保存本文・選択位置・Undo・タブを失わない |
| publish | 原稿編集→公開前チェック→問題箇所→修正→再チェック→出力 | 修正作業へ戻れ、成功・失敗と出力先が確認できる |

各確認点で「続行」「キャンセル」「Escape/ウィンドウを閉じる」「失敗」「失敗後の再試行」「連続クリック」「別原稿・別プロジェクトへの移動」を検査する。長い経路では直前の候補や入力が消えていないことを確認する。本文、画像ハッシュ、採用版、UI選択状態、前面ウィンドウ、操作可能なボタンを具体的な期待値と照合する。

すべての組み合わせを無制限に列挙することはできない。状態遷移を定義して各遷移と連続する2遷移を検査し、複数障害の組み合わせはデータ損失・外部アプリ・非同期処理を優先する。モデルにない経路は探索操作で発見し、登録表へ戻す。

## 3. モックでは代替できない境界を必須にする

ブラウザー+テスト用AI、Rustのデータ処理、実アプリの各証拠を別に記録する。外部アプリ起動、前面表示、OSダイアログ、実WebView、保存済みメタデータの互換性はブラウザーのinvokeモックで確認済みにはできない。

resource-editは必ずStudioのリソース一覧のボタンから開始する。配列形式・elements形式・注釈なし・AI注釈あり・クロップ済み・保護済み・画像欠落を含む匿名化した再現データを用意する。Rustの型に都合の良い新規データだけで検査しない。

起動成功はspawn成功ではなく、対象プロセスの編集ウィンドウが現れ、画像と既存注釈が読み込まれ、実際に編集できることまで確認する。保存成功も完了イベントではなく、保存ファイル・版の追加・原本保持・Studioへの復帰を確認する。

## 4. CIと完了判定をつなぐ

通常のPR検査に接続済みのブラウザー操作テストを維持し、メタデータ互換テストと機能・ケース別の証拠照合を確認する。その後、Linuxの隔離した実デスクトップ検査を必須にする。Windows/macOSのOS連携部分を変更したリリースは、それぞれの実環境で対象経路を確認するまで未確認と表示する。環境がない場合を成功扱いにしない。

操作追加・経路変更・保存形式変更には、対応するシナリオと失敗・復帰ケースを必須とする。登録なし、必要ケースの未実行、期待結果の未検証、古いビルドの証拠、タイムアウト、テスト失敗でゲートを閉じる。既知の不具合で除外する場合も、機能全体を合格と表示しない。

検査結果はシナリオID、ケース、データ形式、OS、ビルド/ソースのハッシュ、成功条件、実行時刻、スクリーンショット、状態ログを含む機械可読レポートとして保存する。合格したスクリプトの本数だけでは完了を判断しない。

## 5. 共通のUI状態遷移で消失を防ぐ

確認ダイアログを開くために親画面の入力や候補を破棄しない。入力中・実行中・候補あり・失敗・採用済みを明示し、閉じる/戻る/再試行の遷移ごとに保持する状態を定義する。外部アプリの起動待ち・編集中・候補保存・起動失敗は押したボタンの近くに表示する。データ保存、画面表示、アプリ起動の異常を無反応や共通のフッターだけで済ませない。

## 導入順と受け入れ条件

1. resource-editの実UI経路と再現データを整備し、今回のelements形式の変換を故意に壊すと検査が失敗することを確認する。
2. 通常CIに接続済みのブラウザー検査を維持し、モック/実バックエンド/実ウィンドウの証拠を区別する。
3. 操作登録表とUIからの収集を接続し、未登録ボタンを追加するとゲートが失敗することを確認する。
4. 上記作業一覧を状態遷移と失敗注入で拡張し、復帰時の入力・候補・原稿保持を必須にする。
5. 前面表示失敗、途中で子プロセス終了、親画面消失、候補のチェック初期化を故意に入れて検査が失敗することを確認する。すべて通るだけでは検査の有効性を判断しない。

この仕組みはバグゼロを保証するものではない。少なくとも「検査していない操作を検査済みと扱う」「直接起動だけでボタンからの連携を確認済みと扱う」「成功経路だけで作業全体を確認済みと扱う」という今回の構造的な漏れを検出して止めることが目的。
