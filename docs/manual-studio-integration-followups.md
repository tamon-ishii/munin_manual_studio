## P05/P07: 画像編集から比較・採用まで

現在の経路は「リソース→編集→候補→履歴・管理→比較→閉じる→履歴・管理→採用→確認」。比較を閉じるとカードが再描画されるため、管理欄を再展開する操作が必要になる。

変更後の候補は「画像を編集→候補を確認→比較・使用箇所→採用」。元の原稿またはカードに戻り、選択版・検索・スクロールを保持する。管理画像は原本から保存注釈を復元し、候補保存まで採用PNGを保持する。通常画像は編集コピーと、使用原稿へ影響する差し替えを区別する。原稿内の管理画像編集がこの契約を経由しない問題は機能統合に先立つ修正対象。

対象仕様: resource-library / screenshot-library / manual-authoring。受け入れは両入口から既存注釈を編集し、候補・原本保持・比較・採用・中止・再試行・途中終了を確認すること。

## P14/P10: HTML出力の入口と下書き作成の配置

3つのボタンを実ブラウザーから押し、実バックエンドで同じ一時原稿と出力先を使って比較した。MkDocsのプロセスはfixture executableであり、実MkDocsの確認とは区別する。

| 現在の入口 | action | draft | 違い |
| --- | --- | --- | --- |
| MkDocsでビルド | build-mkdocs | true | 下書き検査。MkDocsがない場合にHTML未作成としてエラーにする |
| 下書きビルド | build | true | 下書き検査。同じbuilderを使用するがMkDocs不在時の扱いが異なる |
| 完成版ビルド | build | false | 厳格な公開前検査。問題があれば既存出力を保持して停止 |

変更案は「HTML出力」の入口を一つにし、通常の出力と「問題が残っていても確認用に出力」のモードを説明付きで選ぶ。バックエンドの既存build互換は維持し、UIのHTML出力はMkDocsがない場合に成功表示しない。公開前チェックと出力フォルダーを開く操作は独立した目的なので残す。AIで全体の下書きを作る操作は執筆側へ移す。

実操作で「リンク欠落→完成版失敗→既存HTML不変→公開前チェック→該当箇所へ移動→修正→再チェック合格→完成版」を確認した。変更後もこの往復を保持し、同じ原稿を繰り返し選ばせない。

対象仕様: manual-authoring / docs/specs/generation-and-publication.md。個別変更では出力モード、HTML未作成時の表示、原稿と既存出力の保持、下書き作成の配置を仕様化する。

## P03/P04/P11: 挿入入口を維持して共通の保存・復帰を検討する

実バックエンドの8個別ケースで、リソースの取り込み/生成/撮影済み画像、原稿/リソースの作画入口、source/richの管理画像drop、原稿の既存スクショ選択を比較した。カード/作画の5経路では「開始→挿入先→閉じる→再開→Escape→再開→別原稿読込失敗→元原稿へ選び直す→挿入→Undo→再開→別原稿見出しへ挿入→Undo→元原稿」を確認した。作画の指示・候補は保持され、挿入先を閉じても再生成/指示再入力は0回だった。カードは同じ画像を再選択する必要がある。原稿既存スクショでは失敗再試行に方法→画像→プレビューを再度経由する。

処理統合の候補は、挿入先選択と捕捉した位置、失敗時の画像/指示保持、参照取得、Undoを共有すること。提案後の経路は「文脈に合う入口→画像/候補選択→開始時の原稿/位置を既定とする→参照取得と挿入→元の編集画面」、失敗時は同じ候補/挿入先から再試行する。PNG保存を伴うアップロード、既存PNGの参照だけを挿入するカード/作画、撮影手順/採用版を持つスクショは別の保存契約として維持する。両作画入口、カード、原稿での画像選択、source/rich dropは利用文脈が異なるため維持する。

この確認だけで統合UIを実装したり全入口を完了にはしない。手動/AI撮影・OS操作は別途確認が必要。検査範囲と証拠は `docs/manual-studio-verification.md` の管理・生成・撮影済み画像の節を参照する。

2026-10-12の追加検査では、画像ツリーsource/rich、手動/AI撮影、実OSbitmapを含む20個別挿入ケースを同一原稿/位置で照合した。作画では新規生成の指示入力1回、失敗1回→再試行1回と、挿入先取消後の再生成/指示再入力0回を区別して記録する。手動撮影の対象消失時は記録が破棄されるため「Studioへ戻る→新規記録→同じ位置へ挿入」となり、同じ記録の再試行とは扱わない。画像ツリーとリソースカードのdragは同じ受け取り処理だが、通常画像のパスだけを運ぶツリーと採用版のIDを持つ撮影画像の保存契約を区別して維持する。詳細は[挿入条件照合](manual-studio-insertion-matrix.md)を参照する。
