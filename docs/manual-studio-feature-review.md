## 判断基準

機能を減らすこと自体を目標にしない。利用目的、操作を始める場所、生成する結果、保持する状態、戻る経路で判断する。入口が複数あっても作業場所に合っていれば残し、同じ処理へ接続する。別の保存結果を生む操作は違いを表示する。実測していない利用頻度を理由に廃止しない。

## 共通の確認手順

隔離プロジェクトに原稿2件以上、使用中/未使用画像、通常/生成/撮影画像、版候補、保護済み、欠落画像、旧形式、配列/elements画面要素を用意する。ユーザーの設定・原稿を操作しない。実OSでは自作の撮影対象アプリと起動した子プロセスを識別する。

各P番号で、台帳にある全入口から同じ目的を達成する。入口ごとの前提と保存結果の差を記録し、一方の成功を他方の成功に代用しない。次のケースを必要な確認点ごとに実行する。

| ケース | 確認すること |
| --- | --- |
| 正常完了 | 画面の表示だけでなく、本文/画像/版/出力の実データが期待通り |
| 子画面から戻る、キャンセル、Escape | 親の指示、候補、選択、絞り込み、スクロールと元の原稿位置を保持 |
| 失敗→再試行 | 理由と再試行が押した場所で見える、成功済み工程の重複と無反応がない |
| 実行中の連続クリック | 重複起動・挿入・版登録を起こさない |
| 原稿/プロジェクトの切替、対象の外部変更 | 旧結果を別の対象へ適用しない、未保存の原稿を保持 |
| 完了後のUndo、保存、再起動 | 文書操作はUndoでき、保存結果を再読込して復元。資産採用は履歴で戻せる |
| 外部アプリ起動・終了・前面表示 | 実際の編集ウィンドウと対象画像を確認。途中終了で待ち続けない |

使い勝手は、入口発見、パネル往復回数、情報の再入力、重複確認、結果保持、フォーカスによる停止を具体的な操作ログで評価する。正しく動いても毎回同じ入力を要求するなら改善候補とする。AIの待ち時間とUI操作時間を分ける。改善前後を同じfixtureと作業で比較し、確認回数の削減が原本保護や明示採用を損なっていないことを確認する。

## 実装した確認基盤と実操作で得た追加判断

[検査の実行・追加手順](manual-studio-verification.md)を追加した。個別操作の台帳はソース定義698箇所を収集し、初期のグループ契約を個別にレビューするまでは未確認とする。

P05/P07の実操作で、比較を閉じた後のカード再描画によって「履歴・管理」が折りたたまれ、採用前に再展開が必要になることを確認した。作業ログは「履歴・管理→比較→閉じる→履歴・管理→採用→確認」。統合候補は「候補を確認→比較・影響確認→採用」で、比較画面からそのまま採用し、キャンセル時は選択版と一覧位置を保持する。元画像の保護と明示的採用は維持する。このUI変更は未実装。

全体の未実行ケースや実OS証拠の不足が残るため、全機能の動作確認済みとは判定しない。既存のブラウザー検査の成功を未検査入口へ拡張しない。


### P05の入口間の保存契約不一致（実操作で再現）

リソース一覧から配列/elements形式の管理画像を編集する経路は、保存注釈を復元して候補へ追加できる。一方、同じ管理画像を原稿上でホバーし「🎨 画像の編集」を押すと、`edit_document_image` が採用PNGを再エンコードするため編集用注釈メタデータがなくなる。実際のMarkIts入力セッションに `markits:annotations` がないことを確認した。`apply_document_image_edit` は採用パスへ直接書き込む実装で、管理画像の候補採用契約と一致しない。診断では保存せず隔離プロセスを終了した。

この経路を確認済みにはしない。必要な修正案は、管理画像の原稿内編集を一覧と同じ原本・注釈復元と候補保存へ接続すること。普通の画像には編集コピーを使い、資産全体の差し替えと原稿の参照変更を区別する。原稿・プロジェクトを切り替えた場合の復帰、保護、連続クリック、途中終了も同じセッションで扱う。管理画像の保存契約不一致は既存仕様に合わせて修正する。

P14の3ビルド入口の実行比較と統合候補は [個別の統合案](manual-studio-integration-followups.md) に記録した。

### P05 原稿上の管理画像編集の修正（Linux実OS検証済み）

原稿上の画像編集で解決した実ファイルを管理画像の出力パスと照合し、管理画像なら採用版を指定してライブラリーと同じ編集セッションへ渡す。原本・注釈復元と候補保存の処理を共有し、採用PNGへの直接上書きを避ける。通常画像は従来経路のままで、別コピー契約の検証は残る。実OS検査に、原稿の画像ホバー→画像の編集→保存済み矩形の復元→矩形追加→候補保存→採用版/原本/本文の保持を追加した。同一ソース・ビルドで3ケースを実行し、原稿入口では保存矩形2つの復元と3つ目の追加、候補の追加、採用PNG・原本・本文の保持を確認した。個別ケースの完了ゲートも3/3で通過した。途中終了・キャンセル・通常画像コピー・OS間の違いは未確認。

比較画面の実画像も確認した。管理画像の保存sceneからMarkItsに注釈を復元できても、比較画面はPNG内メタデータだけを参照して「注釈メタデータなし」「注釈の保持状況はメタデータから確認できません」と表示する。管理台帳のsceneとPNGメタデータを区別した説明・照合が必要で、画像比較が成功したことを注釈保持の検証完了と同一視しない。証拠は `native-workflow-results/array-compare.png`。

### P04/P13 表示と登録欄の整理

撮影対象の登録UIは「撮影するアプリを登録」に改称し、表示名→起動パス→起動引数の縦順に統一した。リソース一覧の主要操作は「AI撮影 / 撮影 / 読み込み / AI生成 / 再撮影」に短縮し、枠・余白・見出しを縮めた。その他の管理操作は既存メニューに保持する。保存する起動設定と撮影経路は維持する。

### P05 中止・失敗・再試行の追加検査

連携MarkItsのウィンドウを閉じても単体版の常駐処理が適用され、Studioが待ち続ける構造を発見した。連携セッションの「×」だけは中止通知してプロセスを終了し、Studio側も前面へ復帰するよう修正した。実OSケースに、Alt+F4で中止→再編集→子プロセス強制終了→再編集→保護による取り込み失敗→保護解除→再確認で候補保存→再確認して重複なし、を追加する。通常画像コピーと故障注入の独立検査は引き続き未完了。

リソースごとの主要操作も「編集」「コピー」に短縮し、通常の取り込み画像には種別バッジを表示しない。編集エンジンや保存形式は変更しない。

中止・完了前の終了は待機中セッションから外し、再確認しても結果がない処理を残さない。出力取り込みの失敗は編集結果を保持して再試行する。再試行成功後は再確認操作を解除する。この区別を失敗復帰ケースの実OS検査に含める。

### 再撮影の常設メニューを削減（ユーザー指定）

リソース一覧の事前診断・再撮影履歴・旧撮影タグ移行の入口と画面処理を削除し、「その他」を廃止した。「更新」は撮影・生成・再撮影と同じ上部へ配置する。再撮影時の対象チェックと、その場での失敗分再試行は既存経路で維持する。履歴から過去の一括処理を再開するUIは削除対象で、既存保存データとバックエンド互換処理は保持する。廃止した入口は台帳から明示的に除き、残る重複DOM定義の対応も更新した。

### 一覧の密度と作業再開

各リソースの操作を閉じた「操作」メニューへまとめ、一覧行にサムネイル・名前・使用数を表示する。展開状態・履歴の展開・編集版選択はプロジェクトと資産ごとに保持する。別プロジェクトの状態は流用しない。原稿タブの並びと選択中の原稿はプロジェクト別に保存し、起動時に復元する。閉じたタブ・削除済み原稿・空状態・不正な保存データのブラウザー操作検査を追加した。

実OS検査の画像探索を原稿プレビュー内へ限定した結果、採用した画像が一覧には反映されても開いた原稿プレビューには反映されない不具合を検出した。一覧更新時に原稿プレビュー・リッチエディタ内画像・開いている画像タブを再読み込みする。原稿本文と編集履歴は再読込しない。ブラウザー検査にも採用と旧版への復帰時の表示色確認を加え、ファイル変更だけで成功としない。

### P05 通常画像の両入口と失敗復帰（Linux実OS）

リソース一覧は先にコピーを作る一方、原稿上の通常画像編集は元画像へ上書きしていた。デスクトップの共通起動処理で編集コピーを一つ作り、両入口とも元画像と原稿を保持するよう揃えた。完成した編集結果の保存失敗時は同じコピーへの再試行を表示する。原稿への挿入・元画像の差し替えは別の明示操作で、編集終了だけでは使用原稿を書き換えない。

実OSの各入口で「編集→×で中止→編集→子プロセス強制終了→編集→矩形追加→コピーを書き込み禁止→編集終了→保存失敗→書き込み許可→保存再試行」を実行した。成功・中止・異常終了・保存失敗の全段階で元PNGと原稿のハッシュが不変、再試行ではコピー数が増えないことを確認した。通常画像はPNGへ再エンコードされるため、原本保持とコピーの未変更は異なる基準で検証する。中止時の未編集コピーも保持され、利用者の資産を自動削除しない。確認証拠のゲートは `P05.ordinary-resource` / `P05.ordinary-manuscript` の2/2で通過した。

### P03/P04/P11 全挿入入口の保存契約・Undo・FileReaderレースガード

書式ツールバー画像（ファイル選択）、クリップボード貼り付け、エディタへのファイルドロップ、Milkdownリッチアップロードの4経路を同一原稿/意味上のカーソル位置から検査した。入口別の条件差と未確認は `docs/manual-studio-verification.md` を正本とし、この4経路を全挿入入口の完了とは扱わない。
- **変更前の課題**: ファイル選択やドラッグ＆ドロップでは非同期の `FileReader.onload` 待機中に利用者が別の原稿を開いたりプロジェクトを切り替えた場合、古い選択位置や無関係な原稿に画像参照が誤挿入される危険性があった。
- **改善と維持契約**: `FileReader.onload` コールバック突入時に、現在の原稿（`documentState`）、プロジェクト（`projectRoot`）、エディタ内容（`editor.value`）の一致を検証するレースガードを全入口に配備。不一致時は挿入を拒否して警告を表示し、保存済み画像アセット自体は保持する。
- **Undo契約**: Milkdownリッチエディタでの画像ブロック挿入→画像アップロードはProseMirrorの履歴に従い、1段階目で空画像ブロック、2段階目で挿入前の文章へ確実に巻き戻せることを実ブラウザテストで検証した。全入口とも利用文脈（ツールバー・貼付け・ドロップ・WYSIWYG）に直結しているため入口は維持し、内部のガード契約を統一した。

### P09/P10/P12 レビュー→修正案→Diff→部分採用→次の指摘と再起動履歴

読者目線レビュー、校正、画像説明の指摘から修正案を作成し、Diff確認を経て部分採用し、次の指摘へ連続して進むワークフローを検証・改善した。
- **指摘追従とDiff採用**: 校正指摘を採用（adopt）して本文文字数が変動しても、原稿の再アンカー計算により後続の読者指摘（old B）が正確に追従し、該当箇所ジャンプと修正案作成が継続できることを確認した。
- **セッション永続化と再起動履歴**: 読者レビュー結果（`manual-studio-reader-review:${root}:${page}`）、全文下書き候補（`manual-studio-draft-candidate:${root}`）、およびAI実行ログ（`manual-studio-ai-logs:${root}`）のローカル永続化を実装。レビュー結果パネルを閉じてブラウザをリロードした後も「レビュー結果を再表示」から指摘一覧を復元可能にし、実行中の中断（キャンセル）や未完了再起動時にも「中断」ログが確実に記録されることを確認した。

### P01/P02/P06/P08/P13/P15 外部競合・設定再試行・旧形式移行・保護/共有・再撮影部分失敗再試行

列挙した通常操作、設定、資産管理、再撮影、互換機能のシナリオを、実バックエンドまたはブラウザーの模擬経路で検査した。全入口・全OSの確認完了を意味しない。
- **P01/P02（競合と未保存保持）**: 原稿保存待機中に外部からファイルが書き換えられた場合、Studioは外部変更を上書きせず保存エラーバッジを表示して手元の編集ドラフトを維持。別プロジェクトへの切替時の未保存警告で「キャンセル」を選ぶと元の原稿とドラフトが完全に保持される。
- **P13（設定保存失敗再試行）**: 設定保存時の通信障害時にエラーを表示し、入力内容と既存設定ファイルを保持。再試行ボタンで正常保存できる。
- **P15（旧形式互換）**: 旧AIタグを含む文書を開くだけではディスクを上書きせず、旧リビジョンでの移行要求は拒否。明示的移行でバックアップ（.bak）を作成して1回限り安全に移行し、重複移行を防止。
- **P06（保護と共有）**: 保護された画像は採用が無効化され、削除が拒否され、派生画像との共有関係が確認でき、原本ハッシュが保持される。
- **P08（再撮影部分失敗と再試行）**: 複数画像の再撮影で1件成功・1件失敗（部分失敗）が発生した場合、成功分は新候補として保存され原本は不変、失敗分も原本画像が不変で保持され、「失敗分だけ再試行しますか？」の確認ダイアログから再試行して全完了となることを検証した。

### P05/MarkIts ネイティブ故障注入と変換復帰不変性

`scripts/test_manual_studio_native_faults.py` を実行し、配列形式変換、elements形式変換、復帰処理の3種類の変異体（mutants）を一時ディレクトリに生成・コンパイルして実画面経由で検査した。すべての変異体が意図したエラー（画面要素データ読み込み不可、原稿予期変更）で拒否され、通常バイナリおよび通常ソースが不変であることをSHA-256ハッシュで検証した。証拠は `native-workflow-results/faults/result.json` に記録された。


### P03/P04/P11 管理画像/作画候補/既存スクショの8個別挿入ケース

カード3経路、作画の原稿/リソース2入口、source/rich管理画像drop、原稿既存スクショの8経路を、同じ原稿/意味上のカーソルと決定的なPNGで検査し個別証拠へ接続した。キャンセル/失敗時の候補・指示・原稿保持、別原稿への挿入、実保存/Undo、原本・生成履歴・採用版保持を入口の条件に応じて確認した。接続状態/通信失敗/dragイベントは注入を区別する。手動/AI撮影・OS操作と全入口の条件は未完了。

入口は作業文脈に合わせて維持し、参照取得・挿入先・失敗再試行・Undoの処理統合を候補とする。作画では挿入先取消後の再生成/指示再入力は0回、カード/原稿既存スクショでは再開時に画像選択の往復が残る。変更前後の経路と維持する保存契約は `docs/manual-studio-integration-followups.md` のP03/P04/P11節へ記録した。

2026-10-12の同一ビルド再検査では、画像ツリーsource/richの2入口を含む20個別挿入ケースの条件を確認した。手動/AI撮影と実OSbitmapの取消・失敗再試行・別原稿、作画の新規生成失敗再試行を追加し、リッチ編集の待機画像がCtrl+Z後に再挿入される不具合と、別画像のUndoで独立した待機画像まで失う不具合を修正した。[挿入条件照合](manual-studio-insertion-matrix.md)と各結果の`steps`/`workflow`を根拠に4.1を完了とした。全登録のレビューや全OSの合格は意味しない。
